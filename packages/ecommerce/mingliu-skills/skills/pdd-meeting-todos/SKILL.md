# 拼多多日会待办同步

## Overview

每个工作日把当天「拼多多每日例会」的待办同步进会议待办表。**只新增：绝不修改、绝不删除待办表里已有的记录。** 同一场会只同步一次；人工删掉过的待办永不写回。

## 工作区文件

都在智能体工作区（当前会话的工作目录）的 `pdd-meeting-todos/` 下，不放在技能目录里：

- `config.json`（管理员放置，必需）：
  ```json
  {
    "meeting": { "base_token": "<会议信息整理 Base>", "table_id": "<会议信息整理表>" },
    "todo": { "base_token": "<会议待办 Base>", "table_id": "<会议待办表>" },
    "organizer": "<日会组织者姓名>",
    "meeting_keyword": "拼多多每日例会",
    "people": { "<姓名>": "<open_id>" }
  }
  ```
  `people` 里的 open_id 必须是在 MO 飞书连接下查到的值（open_id 随飞书应用不同而不同）。缺少 `config.json` 或其中的表：停止，报告「缺少 pdd-meeting-todos/config.json 配置」，不猜测表。
- `synced.json`（技能读写）：已同步的会议，按会议日期记，`{"meetings": {"YYYY-MM-DD": {"会议名称": "拼多多每日例会MMDD", "at": "<ISO 时间>", "records": [{"id": "rec…", "待办摘要": "…"}]}}}`。待办摘要随写入一起记下，记录被删后靠它写排除清单。
- `exclusions.json`（技能读写）：人工删除过、永不再写入的待办，`{"exclusions": [{"会议名称": "…", "会议日期": "YYYY-MM-DD", "待办摘要": "…", "删除发现于": "YYYY-MM-DD", "原因": "…"}]}`；文件不存在视为空清单。人工也可以往里加。

## 执行流程

0. **发现人工删除**：对 `synced.json` 里最近 14 天的会议，按 `records` 的 id 用 `lark-cli base +record-get`（只读）核对待办表；已经不在表里的记录是人工删的，把 `synced.json` 里记下的「会议名称 + 待办摘要」追加进 `exclusions.json`（`删除发现于` 填今天、`原因` 填「人工删除，尊重人工判断」）。
1. **找待同步的会**：范围 = 最近 7 天（含今天）。用 `lark-cli base +record-search`（只读，按会议名称含 `meeting_keyword` 搜索，`--limit 200`；用前先看 `lark-cli base +record-search --help`）读 `config.meeting` 表，**不要只读 `+record-list` 的默认第一页**；结果满一页就用 `--offset` 翻页。挑出范围内由 `organizer` 组织的拼多多日会（同一天多场取 `organizer` 那场），去掉 `synced.json` 里已有日期的。一场都没有 → 结束，报告「今天无拼多多日会，未同步」（或「最近 7 天的日会都已同步」）。以下 2~9 步按日期从早到晚逐场处理。
2. **已同步检查**：会议名称记为「拼多多每日例会MMDD」（如 0907）。用 `+record-search` 在待办表按会议名称搜索（同样翻页读全），只算**创建时间在该会议日期当天或之后**的记录（避开往年同名）；已有 → 视为已同步，把这些记录（id 与待办事项）补记进 `synced.json` 该日期下，不再写入。
3. **读纪要**：读该记录「完整会议纪要」字段里的智能纪要链接（docx，`lark-cli docs +fetch`，只读），提取「待办」板块的全部条目（checkbox 内容，含条目内的执行人标注）。读不到（无权限、链接缺失、纪要还没生成）→ 这场不写入，报告原因；下次运行仍在 7 天范围内会再试。
4. **交叉核对口述待办**：打开纪要「相关链接」中的文字记录（逐字稿）文档，读取会议末尾主持人口述的待办清单；口述清单里有、但纪要「待办」板块缺失的条目（如素材上新、跟进类）也纳入本次同步。
5. **排除清单过滤**：读 `exclusions.json`，与某条「会议名称（同一会议日期）+ 待办摘要」意思相同的待办跳过，并在报告中列出跳过了哪些。
6. **负责人**：纪要条目中「来自X」表示提出人而非执行人；负责人优先按条目中明确标注的执行人（cite 标签）填写，open_id 取 `config.people`；`people` 里没有这个人或无法判断执行人 → 负责人留空，并在待办事项文本中注明实际跟进人。
7. **截止日期**：条目标注了明确时间（如「本周日」「下周一」）时，按会议日期推算并填写具体日期；无明确时间不填。
8. **写入**：先用 `lark-cli base +field-list` 确认待办表可写字段；把这场的待办写成 JSON 文件（工作区 `pdd-meeting-todos/batch-YYYYMMDD.json`，`{"fields": [...], "rows": [[...], ...]}`，会议名称字段填「拼多多每日例会MMDD」），再在工作区目录下单独运行（`@` 参数加单引号，bash 和 PowerShell 都按字面传给 lark-cli）：
   ```bash
   lark-cli base +record-batch-create --as user --base-token <todo.base_token> --table-id <todo.table_id> --json '@pdd-meeting-todos/batch-YYYYMMDD.json'
   ```
   不用管道、不在命令里拼别的命令。只用这一个写入命令，**不用** `+record-upsert`、`+record-batch-update`、`+record-delete`。
9. **记账**：写入成功后把返回的 `record_id_list` 与对应的待办摘要记进 `synced.json` 该日期下。写入报错时先按第 2 步重查待办表：已经写进去了（例如超时但飞书已处理）→ 补记进 `synced.json`，不重写；确实没写进去 → 不记，报告原因，下次运行在 7 天范围内会再试。

## 完成报告

逐项说明：会议名称、纪要待办条数、口述补充条数、排除跳过条数（列出）、写入条数与 record_id、负责人留空的条目及原因。长期纪律：只增不改；排除清单优先级最高；负责人无法判断留空。
