# 投流 ROI 巡检逻辑

## 日期语义

### 内部日报链路（断点续算）

- 统计窗口**按断点续算**（2026-09-20 用户拍板，与外部提醒链路同机制）：窗口 = 日报链路断点后一天 ~ T-1；正常每天运行时窗口即 T-1 单日，补跑覆盖多天时需在日报中注明窗口。
- 首次运行（无断点）：初始化窗口 = **T-1 单日**，预览开头注明「首次运行：窗口起点请人工核对」，用户核对确认后才发送、才写断点。
- 断点后一天 > T-1（本窗口已发送过）：本轮不重复统计、不再发送，只告诉用户上次已覆盖到哪天。
- 窗口以配置文档「数据窗口」当前值为默认基准；用户指令可临时覆盖本次运行的窗口，不回写配置。

### 外部提醒链路（断点续算）

- **调度**：正常每周一、三、五 10:00 运行（以调度配置为准）；用户明确要求时可临时运行，其余日子该链路静默。
- **不按固定 T+N 窗口**：统计窗口由外部链路断点决定（机制与内部日报链路相同，断点各自分键）——
  - 断点文件存在：窗口 = **断点日期的后一天 ~ T-1**（补充统计上次未覆盖的天数，1 天或多天均可）。
  - 断点文件不存在（首次运行）：初始化窗口 = **T-1 单日**，预览注明「首次运行：窗口起点请人工核对」。
  - 断点后一天 > T-1（无新增数据）：本轮外部链路跳过、不推送，内部日报照常并说明。
- 某个服务商某天缺数据：照常统计，缺失情况在内部日报「数据完整性」列明，不猜测补数。
- **全部子表都没有 T-1 记录**（多半是当天还没采集）：本轮窗口截止日退到最后一个有数据的日期，T-1 不计入、断点也不越过它，预览注明「T-1 数据尚未入表，留到下次统计」。

### 断点文件规范

- 路径：智能体工作区（当前会话的工作目录）下的 `roi-inspection/checkpoint.json`，目录不存在就建；不放在技能目录里（技能更新会覆盖技能目录）。
- **按链路分键**（2026-09-20 用户拍板：统计窗口统一断点续算，双链路仍独立）：顶层分 `internal`（内部日报链路）与 `external`（外部提醒链路）两个对象，互不读写对方键。每链路字段：`last_covered_date`（上次统计截止日，YYYY-MM-DD）、`last_window`（上轮统计的起止日期）、`last_run_date`（上轮运行日期）、`updated_at`；`external` 额外含 `pushed_providers`（上轮已推送的服务商）。
- **内部日报**：发送成功后写 `internal`，`last_covered_date` = 本轮窗口截止日；发送失败或数据读取失败不写，下轮按原断点重新补算。
- **外部提醒按服务商落盘**：每发完一家（不论成败）立即把结果写进 `external.pending`：`{"window": [起, 止], "sent": [发送成功的服务商], "uncertain": [结果不确定的服务商]}`。本轮所有应推服务商都已「发送成功」或「结果不确定」时，`last_covered_date` 前移到窗口截止日并清空 `pending`；有服务商发送失败时不前移。
- **下轮遇到 `pending`**：窗口起点与 `pending.window` 起点相同时，`sent` 与 `uncertain` 里的服务商本轮不再推送（预览中标「上轮已推送」或「上轮结果不确定，请核对」），只推送其余服务商。
- 仅预览未发送：不写任何键，下轮重新补算同一窗口。
- 断点只前移、不回退；写入前先重新读取文件，新值早于文件里的 `last_covered_date` 时不写。
- 各链路只读写自己的键（`internal` / `external`），不读、不写对方断点——保持双链路独立。

## 数据源

- 站外投流数据 Base：链接与各子表 table_id 见配置文档「数据源映射」。
- 每服务商一张子表（table_id 见配置文档「数据源映射」），字段：日期、投放平台、账户id、账户名称、消耗、有效GMV、有效ROI、服务商归属。
- 读取统计窗口内（按「日期」字段过滤）的记录。
- 账户策略表已停用：巡检不再读取策略表及其「状态」列，不再进行「测试中」账户跳过。

## 计算口径

1. 读取各服务商子表统计窗口内记录（窗口按链路各自断点续算确定，见「日期语义」），按「服务商归属」确认归属。
2. **服务商整体有效 ROI** = 该服务商窗口内有效 GMV 合计 ÷ 窗口内消耗合计。
   - 消耗合计 = 0 → 记「无数据」（不当作 0 ROI，也不判定）。
3. **账户汇总有效 ROI** = 该账户窗口内有效 GMV 合计 ÷ 窗口内消耗合计。
   - 消耗为 0 或无法计算 → 不列入低 ROI 提醒，日报中说明。
4. 优先用有效 GMV 与消耗合计，**不直接平均每日 ROI**；按服务商和账户分别汇总。
5. 单日有效 ROI 由 Base 提供（有效GMV ÷ 消耗），仅作参考，不以每日 ROI 平均值作判定依据。

## 判定规则（双链路独立，服务商整体优先）

- **内部群与服务商群是两条独立推送链路**：内部日报（内部群，每天一次、即使全部正常）与服务商群 webhook 提醒在判定、确认、执行、幂等上完全分开——日报发送不依赖服务商群推送决策，服务商群推送不依赖日报是否发送，二者互不触发、互不阻塞。

- 账户低 ROI：账户汇总有效 ROI < 当前预警线（配置文档「巡检参数」当前值）。
- 服务商整体：整体有效 ROI ≥ 预警线 →「达标」；< 预警线 →「未达标」；无数据 →「无数据」。
- **是否推送外部服务商群，只看服务商整体有效 ROI**：
  - **正常提醒（推送）**：服务商整体有效 ROI < 预警线（未达标）→ 生成该服务商 webhook 提醒文案，待用户对该链路单独确认后推送；与日报发送无关。
  - **不推送**：服务商整体有效 ROI ≥ 预警线（达标）→ **即使名下存在低 ROI 账户，也不推送外部服务商群**；低 ROI 账户仅纳入内部日报「③ 低 ROI 账户明细」列示（组标题标注整体达标）。
  - 整体「无数据」但名下存在低 ROI 账户 → 按「正常提醒」推送，整体状态标注「无数据」。
  - 无低 ROI 账户 → 无论整体是否达标，一律静默不推送。
- 全部子表记录均参与判定（账户策略表已停用，无跳过规则）。

## 空值与缺失处理

- 某天记录缺失 / 字段为空：按已有记录计算，缺失情况在日报「数据完整性」说明；不猜测补数。
- 消耗为空 / 为 0：无法计算 ROI 时标「无数据」或「无法计算」，不按 0 处理。
- 数据读取失败 / 字段缺失 / 服务商无法识别 / webhook 缺失：不猜测、不发送错误提醒，在内部日报列明失败原因与待处理项。

## 幂等防重

- 幂等键按链路分开：**内部日报 = 统计窗口 + 内部群**（每天最多一次）；**外部提醒 = 统计窗口（断点续算日期区间）+ 服务商**。
- 不得对同一服务商同一统计窗口重复推送（跨运行靠断点文件的 `external.pending` 判断）；已推送过的组合在日报中体现为「已推送」。

## 只读闸门

- 默认只读：只读取数据与配置，不修改任何在线数据、不写回 Base、不回复群内消息。
- 唯一写入是工作区断点文件，且只在对应链路发送完成后写。
- 定时运行时没有人能确认：只把预览留在本次会话，等用户回到该会话回复确认后再发送。
- **预览确认闸门（两条链路统一）**：内部日报与外部提醒在每次运行（含定时自动运行）时，都必须先把完整内容以只读预览交付用户，未经用户确认不发送任何一条链路；用户确认后仅发送被确认的链路，确认只覆盖当轮。
- 用户明确说「正式推送 / 发送」或明确授权时，才进入发送流程。
- 授权按链路区分：说「发日报」只走内部群链路；说「推送服务商群」只走 webhook 链路；未指明时向用户确认要执行哪条链路，不合并执行。
